# ADR 0031: 5차 검수 정정 — 저장소·데이터셋·동기화·프리라벨·관계·평가·가명

- 상태: 채택
- 날짜: 2026-10-07
- 관련: ADR 0007(데이터셋), 0013·0025(평가 게이트), 0015(검수 결과 보호), 0021·0027(가명),
  0026(프리라벨·관계), 0028(생애주기 기록·동기화), 0029(검수 완료와 생애주기)
- 계약(DB 스키마·JSON Schema) 변경 없음. Alembic 리비전 없음.

## 배경

5차 검수에서 스키마·동기화·프리라벨·관계·평가·학습·데이터셋 모듈의 버그를 확인했다. 모두 코드를 읽고
합성 입력으로 재현한 뒤 회귀 테스트와 함께 고쳤다.

## 결정

1. **판정된 모델을 candidate로 되돌리지 않는다** (`repository.set_model_status`). candidate는 등록 때만
   갖는 초기 상태다. 되돌리면 decided_at이 채워진 candidate가 되어 `ModelVersion` 검증기를 어기고, 이후
   `get_model_version`이 그 행을 읽지 못했다. 이제 candidate를 주면 DB에 닿기 전에 `ValueError`.
2. **`set_lifecycle`은 시간대 없는 `at`을 UPDATE 전에 거부한다.** 예전에는 sessions 행을 바꾼 뒤
   기록 단계에서 거부해, 호출자가 예외를 잡고 커밋하면 기록 없는 전이가 남았다.
3. **데이터셋 빌드와 사용 중지의 생애주기 기록에 시각·실행자를 남긴다.** 빌드는 `at=now`,
   `actor="dataset:<버전 ID>"`. `withdraw_session`은 `at=now`, `actor` 인자(기본 "withdraw");
   `dlp dataset withdraw`는 `--actor`, 없으면 `DLP_ACTOR`/OS 사용자.
4. **데이터셋 빌드 후보는 프라이버시 승인된 세션이다 (ADR 0007 유지).** ADR 0029 배경의 "human_verified
   세션만 분할에 넣는다"는 서술이 틀렸다. 판단 근거:
   - ADR 0007 결정 5가 후보를 프라이버시 승인 세션으로, human_verified는 split_assigned 전이 조건으로
     정했다. WP7 완료 기준에도 검증 조건은 없다.
   - 골든셋은 프라이버시 승인 세션에서 제안(`propose_golden_set`)한 뒤 사람이 라벨링한다. 빌드가
     human_verified만 받으면 라벨링 중인 골든 세션이 후보에서 빠져, 그 작업자·장소를 막는 일을
     `golden_sessions`(후보 밖 골든)로만 하게 되고 골든 분할 자체가 비게 된다.
   - 재학습은 자동 원본과 수정본의 차이를 쓰고, 내보내기는 라벨 검증 상태로 거른다 (ADR 0018).
     검증 전 세션의 라벨이 스냅샷에 있어도 미검수 라벨은 기본 내보내기에 들어가지 않는다.
   그래서 코드는 그대로 두고 ADR 0029 본문을 바로잡았다 (human_verified는 split_assigned 전이 조건).
5. **검수 결과(`history.review_changes`)에서 센서 출처 현재 라벨은 세지 않는다.** 예전에는 states 안의
   센서 라벨(장갑 압력 접촉 등)이 사슬 맨 앞이 모델이 아니라는 이유로 "사람이 추가함(added)"으로 세져,
   운영 지표의 추가율과 원본 보관 기산점을 부풀렸다.
6. **평가 게이트의 지표 이름을 정책을 읽을 때 검사한다.** `dlp_eval.policy.TASK_METRICS`(과제 → 평가기가
   늘 내는 지표, actions는 `segment_f1_<segment_iou>`를 더함)와 `CLASS_METRIC_PREFIXES`(클래스별 지표
   `ap/<클래스>`·`blur_recall/<대상>`)가 기준이다. gate의 primary·guards·max_drop_by에 모르는 이름이 있으면
   `load_policy`가 실패한다. 예전에는 오타가 후보·기존 모두 NaN이 되어 그 비교를 조용히 건너뛰었다.
   `harness.evaluate`는 평가기 출력이 이 목록과 다르면 실패해, 목록이 실제 출력과 어긋나지 않게 한다.
7. **슬레이트의 오디오 정밀화가 `FitError`로 실패하면 슬레이트 맞춤을 쓴다** (`pipeline._slate`).
   예전에는 예외가 `_try`까지 올라가 이미 맞춘 슬레이트 결과까지 신뢰도 0으로 버렸다. 사유는 보고서에
   "오디오 정밀화 실패 (<이유>)"로 남는다.
8. **프레임 시각이 엄격히 증가하도록 같은 ms 프레임을 건너뛴다** (`prelabel.common.strictly_increasing`).
   PTS를 정수 ms로 반올림하므로 고fps·VFR 영상에서 이웃 프레임이 같은 ms가 될 수 있다. MediaPipe VIDEO
   모드는 그 시각에서 예외를 내고, 트랙에는 같은 시각 키프레임이 두 번 들어간다. MediaPipe 손·객체와
   RTMPose 어댑터가 쓴다. 시각은 PTS 그대로이고 프레임 번호는 만들지 않는다.
9. **접촉 추정에 쓸 손 트랙을 정해진 순서로 고른다** (`prelabel.runner.pick_hand_tracks`). 같은 손
   hand21 트랙이 여럿이면 사람·검수된 트랙 → 최근 생성 → 긴 구간 → 라벨 ID 순. 예전에는 조회 순서의
   마지막 트랙을 조용히 썼다. 트랙을 섞지 않는다 (관절 위치의 출처가 흐려진다).
10. **관계 단계 정정** (`relations.runner`): 삭제 레코드를 공용 `episode.retractions`로 만든다(128자 넘는
    ID 줄이기·계약 검증). 재삽입 번호(`-<n>`)는 삭제 레코드를 빼고 센다 (예전에는 두 번째 재삽입이
    `-3`). 새 레코드의 온톨로지 버전은 시각 순 첫 라벨이 아니라 세션의 온톨로지 버전이다.
11. **가명의 세션 부분 치환은 온전한 토큰만** (`export.pseudonym.Pseudonymizer.ref`). 앞뒤가 문자열
    시작·끝 또는 영숫자가 아닌 구분자일 때만 바꾼다. 예전에는 부분 문자열 치환이라 세션 "s1"이
    "s10-…"의 앞부분까지 바꿨다.

## 결과

- 정책 YAML의 게이트 지표 이름 오타는 이제 `dlp eval golden`·재학습 루프 시작 시 바로 드러난다.
- 동일 내용 관계의 재삽입 ID가 `-1`, `-2`, … 로 이어진다. 이미 `-3` 등으로 들어간 과거 레코드는 그대로
  둔다 (라벨은 덮어쓰지 않는다). 다음 번호는 넣은 레코드 수이고, 그 ID가 있으면 다음 번호를 쓴다.
- 생애주기 기록의 실행자로 빌드(`dataset:<버전>`)와 사용 중지 실행자를 계보·감사에서 구분할 수 있다.
