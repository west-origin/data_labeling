# 첫 실영상 파일럿 2026-10-22 (iPhone 13 가슴 장착, 가사 영상)

사용자가 처음 준 실제 촬영 영상 한 편을 개발 서비스 위의 실제 파이프라인(`dlp …` 명령)에 끝까지 넣어
본 기록이다. 정답 라벨이 없으므로 **아래 숫자는 정확도가 아니라 산출량·실행 시간·눈으로 본 표본 판정**이다.
영상·프레임·잘라낸 이미지·영상에서 읽은 글자(주소·이름)는 저장소에 넣지 않았다. 이 문서에는 집계 수치만
적는다. 남긴 문제는 `issues.yaml`의 F-PMS-31~33, F-PAR-59~61, F-SCH-26이다.

**데이터 용도 (2026-10-24):** 이 데이터는 당분간 판매하지 않고 사내 모델 개발에 쓴다. 문서상의 용도
변경일 뿐 라이선스(비상업 가중치 금지)·개인정보·내보내기 규칙은 그대로다 (ADR 0058 6절).

동의서 버전과 촬영 시각은 실제 값이 아니다. 실제 값을 받으면 새 세션 ID로 다시 수집한다.

### 방향: 태그가 틀렸다 (F-PMS-33, 고침)

`dlp media probe`는 표시 회전 -90°를 보였고 `dlp media prepare`가 태그대로 돌린 1080x1920 사본을 만들었다
(세션 `pilot-real1`). 그런데 그 사본은 착용자 몸통·팔이 화면 오른쪽에서 들어오는 옆으로 누운 화면이었다.
저장 픽셀을 보니 몸통이 위쪽 가장자리에 있어, 폰이 가슴에 가로로 거꾸로 달린 채 방향 고정(세로)으로
녹화된 것으로 본다. 태그를 무시하고 각도를 지정하는 `dlp media prepare --display-rotation <반시계 각도>`를
더해 180°로 바로 세운 1920x1080 사본을 만들고 새 세션 `pilot-real2`로 수집했다. 두 세션은 같은 영상의
두 방향이라 방향이 모델 출력에 주는 영향을 비교할 수 있다 (6절).

|---|---|---|---|

| 전신(RTMPose) | `dlp prelabel run` | 약 52분 (첫 일괄 실행에서 관찰, 아래 주의) | 51분 39초 |
| 관계 | `dlp relations run` | 18초 | 19초 |
| 행동 구간·설명 | `dlp actions run` | 종료 코드 2: VLM 서버 없음 (실행 안 함) | 같음 |
| AI 1차 검수 | `dlp aireview run` | 종료 코드 2: 사내 VLM 서버 없음 (실행 안 함). `status`: 판정 대상 단위 12964, 승인 전 | 같음 (단위 12600) |
| 검수 작업 | `dlp review create` | 만들지 못함 (5절) | 같음 |

- 이 CPU에서 342초 영상 하나의 전체 처리는 약 4~5시간이다. OWLv2(프라이버시·도구 각 684회 추론)가
  절반을 넘게 쓴다. 프레임 간격(`frame_stride_ms`)은 정책 값 그대로 두었다.
- `dlp prelabel run`을 한 번에 돌리면 모든 단계를 한 트랜잭션으로 쓰고 끝에 커밋한다. 첫 일괄 실행은
  도구 단계 도중 실행 환경의 2시간 제한으로 끊겨 1시간 50분 계산이 모두 롤백됐다(DB에는 아무것도 남지
  않음, 멱등이라 다시 돌리면 된다). 그래서 위처럼 `--skip`으로 나눠 단계마다 커밋했다. 긴 영상은 나눠
  돌리기를 권한다. pilot-real1의 전신 결과는 이 롤백으로 없다.
- 디스크: SeaweedFS는 디스크의 1%(여기서 2.5 GB)보다 여유가 적으면 쓰기를 거부하고, `dlp ingest`는
  boto `InternalError` 추적만 보인다 (F-PMS-32). 남은 에이전트 작업 트리의 가상 환경을 지워 여유를 늘린 뒤
  `docker restart dlp-seaweedfs-1`로 풀렸다. 수집 뒤 로컬 준비 사본은 지웠다(원본 버킷에 있음).

## 4. 내부 파라미터·화각 판단

결론: **이번 파일럿은 정책 기본값(가로 90°, 출처 `hfov_approx`)으로 돌렸고 계약은 바꾸지 않았다.**
사양에서 계산한 값을 `calibrated`로 적지 않았다. 문제는 F-PAR-59로 남겼다.

### 렌즈 확인 (2026-10-23 추가)

사용자가 이 영상을 **iPhone 13 0.5x 초광각(35 mm 환산 13 mm)** 으로 찍었다고 확인했다. 아래 손 크기
역산이 가리킨 초점 약 700 px와 맞는다.

- 공칭 화각 셈: 환산 초점은 대각 43.3 mm 기준이다. 4:3 센서면 환산 폭 34.6 mm·높이 26.0 mm이고, 16:9
  영상은 폭을 다 쓰고 위아래를 자른다고 보면 환산 높이 19.5 mm다. 그러면 1920x1080 바로 세운 사본은
  **긴 변(1920 px) 약 106°, 짧은 변(1080 px) 약 74°, 대각 약 115°** 이고 초점은 양쪽 모두 약 **720 px**
  (960 / tan 53° ≈ 540 / tan 37°)다. 옆으로 누운 사본(1080x1920)도 같은 초점 720 px다(변만 바뀜).
- 정책 기본값과 비교: pilot-real1(1080 px 변에 90°, 초점 540 px)은 0.75배, pilot-real2(1920 px 변에
  90°, 초점 960 px)는 1.33배다. 손 맞춤 거리는 초점에 비례하므로 pilot-real2의 손 맞춤 손목 z
  (중앙값 0.67 m)는 초광각 공칭값이면 약 0.50 m가 된다. 손 크기로 셈한 손 거리 중앙값은 약 0.57 m(아래 표
  0.5x 행)로 팔 길이 안이다.
- 여전히 **캘리브레이션이 아니다.** 손떨림 보정(표준·액션 모드)이 화면 가장자리를 잘라 초점이 수 %~수십 %
  커질 수 있고, iPhone은 영상에 렌즈 왜곡 보정을 적용하지만 초광각의 남은 왜곡(가장자리 손·물체 위치
  오차)은 재지 않았다. 사양에서 셈한 값을 매니페스트 `intrinsics`(=`calibrated`)로 넣지 않았고 정책
  `default_hfov_deg`도 바꾸지 않았다. 다음 실행부터 바르게 하려면 같은 렌즈(0.5x)·해상도·fps·손떨림
  보정 설정의 체커보드 영상으로 `dlp calib intrinsics`를 등록한다.
- 기기 ID: pilot-real2 매니페스트에는 `iphone13-lens-unconfirmed-1080p30`이 이미 들어 있다.
  `dlp calib assign iphone13-ultrawide-0.5x-1080p30 pilot-real2`는 매니페스트 기기가 앞선다는 이유로
  충돌(종료 코드 2, 아무것도 쓰지 않음)로 끝났다(설계대로, `assign_session_camera`). 수집 기록의 기기를
  바꾸는 정직한 절차는 지금 없다. 그래서 (1) 다음 촬영·재수집 매니페스트는
  `calibration.camera_id: iphone13-ultrawide-0.5x-1080p30`으로 적고, (2) 이 체커보드로 pilot-real2를
  다시 돌릴 때는 새 세션 ID로 다시 수집한다. 기존 ID 아래에 캘리브레이션을 등록하는 우회는 하지 않는다
  (렌즈 미확인이라는 이름과 맞지 않는다).

- 이유 1: 지금 계약의 출처 값은 `calibrated`·`hfov_approx` 둘뿐이다. 사양 화각을 매니페스트 `intrinsics`로
  넣으면 `calibrated`로 기록돼 출처를 속인다. 정책 `default_hfov_deg`는 모든 세션에 한꺼번에 적용된다.
- 이유 2: 어떤 렌즈로 찍었는지부터 확실하지 않다. 초점 거리(픽셀, 방향과 무관)를 후보별로 놓고 손바닥
  픽셀 길이(손목-가운데 손가락 뿌리, 두 사본 모두 사분위 약 94 / 113 / 139 px)와 손 크기 사전값 0.09 m로 거리를 셈하면:

| 가정 | 초점 거리 (px) | 손 크기로 셈한 손 거리 중앙값 | 0.75 m 초과 비율 |
|---|---|---|---|
| pilot-real1 실행값 (1080 px 변에 90°) | 540 | 0.43 m | 1.4% |
| 0.5x 초광각 사양 근사 (긴 변 약 108°) | 약 700 | 0.56 m | 13.7% |
| pilot-real2 실행값 (1920 px 변에 90°) | 960 | 0.77 m | 53.1% |
| 1x 주 카메라 사양 근사 (긴 변 약 65°, 짧은 변 약 39°) | 약 1500 | 1.20 m | 90.6% |

  가슴에 단 카메라에서 자기 손까지는 팔 길이(약 0.6~0.7 m)를 넘기 어렵다. 1x 주 카메라라면 손이 대부분
  1 m 넘게 떨어져 있어야 해 맞지 않는다. 앞선 빠른 측정에서 깊이 모델로 잰 손바닥 길이가 손 크기와 맞는
  화각도 1080 px 변 기준 약 60°(초점 약 940 px)였다. 두 근거 모두 **초광각(0.5x)이거나 손떨림 보정이 화면을
  넓게 쓰는 모드**를 가리키지만 추정일 뿐이다. 사양 값을 넣어도 어느 렌즈인지 모르면 더 틀릴 수 있다.
- 바로 잡는 길: 같은 iPhone·같은 렌즈·같은 해상도·같은 손떨림 보정 설정으로 체커보드 영상을 찍어
  `dlp calib intrinsics <기기> board.mp4 --board 8x5 --square-mm <칸>`으로 등록한다
  ([카메라 캘리브레이션](camera-calibration.md)). 그러면 출처가 정직하게 `calibrated`가 된다. 손 크기는
  `dlp calib palm w-pilot01 <m>`로 잰 값을 넣는다.
- 기기 ID는 pilot-real1에 `iphone13-main-1080p30`으로 적었는데 렌즈가 확인되지 않았다. pilot-real2는
  `iphone13-lens-unconfirmed-1080p30`이다. 렌즈를 확인하면 `dlp calib assign <기기> <세션>`으로 맞는 기기에
  잇는다 (매니페스트 값이 앞서므로 새 세션으로 다시 수집하는 편이 깔끔하다).

## 5. 검수 화면

- CVAT 서버 이미지가 없어(지시대로 받지 않음) 블러 검수 작업(`--stage privacy`)을 만들지 못했다. 블러 검수는
  CVAT 경로뿐이다.
- 블러를 사람이 검수·승인하기 전에는 라벨링 작업을 만들 수 없다. `dlp review create … --stage labeling
  --tool label_studio`는 CVAT 로그인을 먼저 시도해 연결 거부 추적으로 끝났다(`--no-cvat`을 함께 줘야 한다).
  `--no-cvat`을 주면 프라이버시 승인 검사에서 막힌다(정상 동작: 승인 전 라벨링 작업 금지). 승인을 흉내 내지
  않았다.
- Label Studio 서비스 자체는 떠 있고 로그인·프로젝트 목록이 열리는 것만 확인했다(스크린숏은 저장소 밖
  스크래치패드). 이 세션의 작업 화면은 열어 보지 못했다.

## 6. 방향의 영향 (pilot-real1 vs pilot-real2)

같은 영상을 태그대로 돌린 옆으로 누운 사본과 180°로 바로 세운 사본의 비교다. 정답이 없어 어느 쪽이 맞게
찾았는지는 모르고 산출량 차이만 적는다.

| 항목 | pilot-real1 (옆으로 누움) | pilot-real2 (바로 세움) |
|---|---|---|
| 블러 트랙 | 5247 | 5243 |
| 블러 면적 합집합 중앙값 / 50% 초과 프레임 | 0.81 / 97.7% | 0.47 / 35.4% |
| 얼굴 트랙 (표본 24개 중 실제 얼굴) | 1671 (0) | 1703 (0) |
| 손 있는 프레임 / 두 손 | 77.7% / 25.3% | 77.9% / 24.5% |
| 손목 손 맞춤 성공 | 79.2% | 89.9% |
| COCO 객체 트랙 (person / bed / toilet) | 238 (123 / 59 / 5) | 236 (173 / 5 / 19) |
| OWLv2 도구 트랙 (신뢰도 0.3 이상) | 12414 (340) | 12008 (424) |
| 3D 궤적 (도구 단계 뒤) | 6187 | 2291 |
| 영상 접촉 / 접촉 관계 | 339 / 305 | 178 / 177 |
| 전신 COCO17 트랙 | (롤백으로 없음) | 176 (키프레임 8431, 평균 신뢰도 0.34) |

- 손 검출률은 방향과 거의 무관했다(MediaPipe 손 탐지는 회전에 강하다). 손 맞춤 성공률은 바로 세운 쪽이
  10%p 높다.
- 블러 면적은 바로 세운 쪽이 크게 줄었지만 트랙 수는 같다. 둘 다 그대로는 쓸 수 없다 (F-PMS-31).
- COCO 객체의 bed 오탐은 줄고 toilet 오탐은 늘었다. 도구 오탐 규모는 방향과 무관하다 (F-PAR-60).
- 착용자 몸이 화면 아래에 오는 1인칭 방향이 검수자에게 자연스럽고, 행동 VLM·AI 1차 검수 입력도 같은
  방향을 가정하므로 앞으로는 바로 세운 사본을 쓴다. pilot-real1은 비교용으로 남겼다.

## 7. 막힌 것과 다음에 필요한 것

막힌 것
- 블러 검수·승인: CVAT 서버 + 원본 접근 권한자(`review.yaml reviewers.privacy`)의 사람 검수. 그 전에는 렌더,
  라벨링 작업, AI 1차 검수, 행동 VLM, 내보내기가 모두 막힌다.
- 프라이버시·도구 오탐(F-PMS-31, F-PAR-60): 정답 표본 없이 문턱을 정할 수 없다.
- 행동·AI 1차 검수: 사내 VLM 서버(`DLP_VLM_URL`, `DLP_VLM_URLS`)가 이 환경에 없다.
- 카메라 자세·월드 좌표: 바디캠 IMU가 없다.

사용자에게 필요한 것
1. 같은 iPhone 13·같은 렌즈(0.5x 초광각, 확인됨)·1080p 같은 fps·같은 손떨림 보정 설정의 체커보드
   영상 1편 (보드만, 기울인 자세 15개 이상, 절차는 camera-calibration.md 2절).
2. 촬영 때의 손떨림 보정(표준/액션 모드)·장착 방향(가로·거꾸로) 기록(렌즈는 0.5x로 확인됨). 가능하면 원본 파일(재다중화 전,
   촬영 시각 태그 포함)과 실제 촬영 시각.
3. 착용자 손바닥 길이(손목 주름 → 가운데 손가락 뿌리, 자로 잰 m 값).
4. 실제 동의서 버전, 작업자·장소의 가명 ID 확정.
5. 카메라 자세(6자유도)·월드 좌표가 필요하면 IMU가 있는 GoPro(GPMF) 영상. iPhone 영상에는 IMU 트랙이 없다.
6. 정확도를 재려면 몇 분 구간의 사람 정답(손 좌우·관절, 블러 대상, 도구 클래스). 문턱 조정은 그 뒤에 한다.
7. 온톨로지 범위 결정: 가사(설거지·택배)를 더할지, 촬영을 청소·돌봄 장면으로 맞출지 (F-SCH-26).

## 9. 결과 미리보기 영상과 손 좌우 (2026-10-23 추가)

Label Studio를 열 수 없는 사람에게 결과를 보이려고 `scripts/preview_session.py`(일회용 확인 도구, DB에
쓰지 않음)를 더했다. 개발 DB의 운영 라벨(`current_labels`)을 수집 전 로컬 영상(같은 PTS, 수집 때와 같은
180° 회전)에 그려 540 px 폭 H.264로 쓴다. 원본 버킷은 읽지 않는다. 손 2D(좌우 색, 손끝 강조), 손목 3D
방식·신뢰도·z와 손끝 표본 수, 프라이버시 탐지 박스(블러 적용 없이 테두리만, 대상/탐지기/신뢰도),
COCO·OWLv2 박스(트랙 신뢰도 0.3 미만은 숨기고 개수만), PTS 시각과 범례를 싣는다. 출력(영상·요약 카드)은
개인정보라 저장소 밖 스크래치패드에만 두었다. 시험: `tests/test_preview_session.py`(합성 블러 픽스처).

pilot-real2 205~285 s(설거지 끝 → 바닥 → 택배 상자 개봉)를 보고 적은 것:

- 프라이버시: 프레임마다 대상 박스 6~38개. 얼굴(YuNet) 박스는 싱크·수전·손·바닥에 붙고 실제 얼굴은 없다.
  반사(refl) 박스는 스테인리스 싱크·바닥 광택에 수십 개, 문서·사진·화면(OWLv2) 박스는 상자 면·흰 바닥·
  천에 붙는다 (F-PMS-31과 같은 경향).
- 객체: COCO person 박스가 착용자 자신의 팔·몸통을 크게 덮는다. OWLv2 박스는 0.3 이상만 그려도 rag·
  trash_bag·sponge·dustpan·toilet_brush가 장면과 무관하게 뜬다 (F-PAR-60).
- 손 3D: 손목 손 맞춤 z가 0.3~1.3 m로 흔들린다. 1 m 넘는 값은 팔 길이 밖이다(기본 화각이 초광각보다 좁게 잡힌
  영향 포함, 위 4절).
- **손 좌우가 대체로 뒤바뀐 것으로 보인다 (F-PAR-61, 후보).** 두 손 프레임 2513개 중 88.5%에서 `left_hand`
  손목이 `right_hand` 손목보다 화면 오른쪽에 있다. 바로 세운 1인칭 화면에서 착용자 왼손은 보통 왼쪽 아래에서
  들어온다. 두 손 프레임 표본 6장을 보니 4장이 뒤바뀜, 1장이 맞음, 1장은 두 트랙이 같은 손에 겹쳤다.
  손목시계가 화면 왼쪽 손에 있는 것도 같은 방향을 가리킨다. 어댑터는 MediaPipe가 거울상 입력을 가정한다고
  보고 좌우를 뒤집는데(`hands.input_is_mirrored: false` → `flip_hand`), 이 영상에서는 그 뒤집기가 틀린
  쪽으로 작동한 것으로 보인다. 정답 표본 없이 영상 한 편이라 고치지 않았다.

## 10. 후속 개선 (2026-10-23, 정답 없이 대리 지표로 잼)

사용자가 승인한 순서(그룹 0~5)로 고친 것과 pilot-real2에서 잰 전후 값이다. 정답 표본이 없어 정확도가 아니라
대리 지표(그룹 1에서 더한 `dlp ops quality-proxy`)의 변화다. 다시 돌린 단계만 바뀐다.

### 10.0 손 좌우 (F-PAR-61, 고침)

원인: MediaPipe 손 판정은 손 모양의 좌우성으로 정하고 기준이 거울상 셀카 화면이다. 손등 쪽에서 보는 1인칭
화면은 마주 본 화면을 좌우로 뒤집은 것과 같아, 손 모양 좌우가 거울상 셀카와 같다. 그래서 1인칭은 판정을 그대로
써야 하는데 어댑터가 "바디캠은 거울상이 아님"을 이유로 뒤집었다.

확인(정답 없음, 영상 한 편): 뒤집기 전 원시 판정을 0.5 s 간격 685장(IMAGE 모드)에서 보니 Left·Right 두 손
프레임 49장 중 33장(67%)이 Left가 화면 왼쪽이었다. 같은 프레임을 좌우로 뒤집으면 짝지은 손 341개 중
243개(71%)의 판정이 바뀌어, 판정이 화면 위치가 아니라 손 모양에서 나온다.

수정: 정책 `hands.input_is_mirrored`를 의미가 분명한 `hands.swap_handedness`(1인칭 false, 사람이 비거울상
카메라를 마주 볼 때만 true)로 바꾸고 어댑터 버전에 `hd2`를 넣었다. 손 단계만 다시 돌렸다(9분, 검수 전 이전 손
트랙만 지움). 3인칭 스트림에 정책 하나가 함께 적용되는 한계는 F-PAR-62.

| 대리 지표 (pilot-real2) | 전 | 후 |
| --- | --- | --- |
| 두 손 프레임(2513개) 중 `left_hand` 손목이 화면 왼쪽 | 0.115 | 0.885 |
| 손목 일치 MediaPipe vs RTMPose (쌍 9096) | 0.976 | 0.976 |

### 10.1 정답 없는 품질 대리 지표와 촬영 점검 (그룹 1)

`dlp ops quality-proxy <세션> [--stream] [--out]`(`dlp_eval.proxy`, 기준 `evaluation.yaml proxy`, 읽기 전용)이
운영 라벨에서 잰다: 묶음(박스 계열·클래스, 블러 대상, 골격·손)마다 트랙 수·분당 트랙·길이 분포·짧은 트랙
비율·키프레임 하나 비율, 시각별 탐지 수, 존재 구간의 끊김(분당 구간, 짧은 구간 비율), 손 존재 비율 추정·
손목 2D 떨림(2차 차분 / 손 크기), 두 손 프레임의 화면 좌우, MediaPipe 손목과 RTMPose 손목 일치, 얼굴 블러의
사람 박스·머리 관절 근처 비율, 손 3D(카메라 좌표) 손목 거리 범위 밖·속도·가속도 초과, 손목→손끝 거리

### 10.3 장면 어휘·오탐 의심 힌트·TTA (그룹 3, ADR 0055)

바꾼 것: 도구 질의를 장면(kitchen·bathroom·bedroom·living·unknown)으로 고른다(`--scene`, 사내 VLM 장면 분류,
없으면 unknown = 전체 질의). 블러 오탐 의심(no_head·on_hand·short_flicker·tta_unstable)과 객체 오탐
의심(착용자 몸)을 검수 화면 이슈로만 싣는다(블러·라벨은 바꾸지 않음). TTA는 공용 기하 변환
(`dlp_media.geometry`)으로 변환 화면에서 다시 찾아 지지율을 잰다. 사내 VLM이 없어 장면은 `--scene kitchen`으로
직접 줬다(장면 분류기 자체는 재지 못함).

| 대리 지표 (pilot-real2) | 그룹 2 뒤 (전체 질의) | `--scene kitchen` |

남은 도구 트랙(걸레·스펀지·쓰레기봉투 등)의 맞고 틀림은 정답이 없어 모른다. 장면 질의는 그 장면에 없는 물건의

### 10.4 손 크기 초점 거리 추정 (그룹 4, ADR 0056) — 실영상에서 틀려 기본 끔

3D 단계를 추정을 켠 판으로 다시 돌렸다(80분 + 추정용 깊이 1초 간격). 추정 결과는 **fx 1767 px(가로 57도)**,
표본 140, 퍼짐 0.42로 모든 문턱을 통과했다. 그런데 이 영상의 공칭값(4절, 0.5x 초광각)은 약 720 px다.

| 대리 지표 (pilot-real2) | 그룹 2 뒤 (기본 90도, 960 px) | 추정 초점 1767 px |
| --- | --- | --- |
| 손목 3D 거리 p50 (왼 / 오른) | 0.73 / 0.71 m | 1.23 / 1.16 m |

학습 영상 화각을 전제로 거리를 내므로, 초광각에서 손을 멀다고 답하고 식은 깊이 모델의 화각 사전값(약 57도)을
되돌려 준다. 4절의 "깊이로 잰 손바닥이 맞는 화각 약 60도"도 같은 현상이었다. 합성 시험은 정답 깊이를 써서
드러나지 않았다. 그래서 `depth.focal_estimate.enabled: false`가 기본이 됐고(ADR 0056 개정, F-PAR-65), 이 세션의
3D는 화각 근사로 다시 돌린다. 바로 잡는 길은 여전히 체커보드 캘리브레이션이다(4절). 잘라 낸 박스의 AI 확인
(`dlp review hints --ai`)은 사내 VLM이 없어 파일럿에서 재지 못했다(합성 서버 시험만).

화각 근사로 되돌린 재실행(2026-10-23 17:07~18:17, 70분, `--skip body --skip tools`, 메모리 완화 F-PMS-36 적용판,
최대 RSS 약 5.2 GB)은 끝까지 통과했다. 3D 궤적 801개. 대리 지표는 그룹 2 뒤 값으로 돌아왔다:
손목 3D 거리 p50 왼 0.733 / 오른 0.710 m, 0.15~0.9 m 밖 0.303 / 0.248, 3 m/s 초과 0.029 / 0.036,
가속도 초과 0.002 / 0.006. 같은 실행의 다른 지표: 두 손 프레임의 왼손 화면 왼쪽 0.884, MediaPipe·RTMPose 손목
일치 0.976, 얼굴 블러 키프레임 중 머리 관절 근처 0.047(대부분 오탐, F-PMS-31).

### 10.5 학습 증강 (그룹 5, ADR 0057)

학습 증강(`dlp_train.augment`: 뒤집기·회전·자르기·원근·렌즈 왜곡·광학·1인칭 효과)은 파일럿 데이터로 재지 않았다.
이 세션은 검수 전이라 데이터셋 버전의 학습 분할이 없고, 증강의 입력은 학습·검증 분할 블러본만이다. 정확성은 위치를
아는 합성 프레임에서 변환마다 라벨이 픽셀을 따라가는지(박스·마스크·키포인트·3D 투영), 뒤집기의 손·COCO 좌우
교환, 골든·holdout·원본 버킷 거부로 시험한다. 학습 효과(검증 지표 변화)는 실제 학습기 연동 뒤 잰다.

  본다. 그래서 팔꿈치 3D 대부분에 forearm_length 표시가 붙고 신뢰도가 낮아졌다. 2D 팔꿈치와 팔 골격 자체는
  미리보기에서 화면 밖 팔꿈치를 지어내지 않는 것을 눈으로 확인했다 (정확도 미측정, F-PAR-66).
- 미리보기: 205~285 s, 손목 → 팔꿈치 선과 패널의 팔꿈치 보임·아래팔 3D 길이 (저장소 밖 작업 디렉터리).


## 12. 객체·손 모양 마스크 (2026-10-25, ADR 0059)

SAM 2.1 tiny(ONNX fp32, CPU)를 pilot-real2의 두 구간에 돌렸다. DB에는 쓰지 않았다: 구간만 돌린 결과가 세션 라벨이
되지 않게, 개발 DB의 현재 박스·손 트랙을 읽어 `dlp_prelabel.masks.make_masks`를 수집 전 로컬 영상(같은 PTS, 180°
회전)에 돌리고 결과 라벨을 저장소 밖 작업 디렉터리의 JSON Lines로만 남겼다 (미리보기는 `--extra-labels`로 그 파일을
읽는다). 정답이 없으므로 숫자는 산출량·실행 시간·대리 지표다. 정책은 저장소 기본값(500 ms 간격, 모델 박스 트랙 신뢰도
0.3 이상, 손 프롬프트 = 관절 박스 15% 넓힘 + 손목·손가락 뿌리 점)이다.

- 첫 실행(205~285 s)에서 손이 화면에 없던 250 s 무렵 착용자 셔츠(COCO person 박스, ADR 0058 억제는 손 증거가 있어야

  키프레임 사이에 어긋나 보인다 (보간 없음, F-PAR-69).
- 미리보기: 두 구간, 반투명 채움 + 윤곽(손 초록·주황, 객체 클래스 색), 패널에 보이는 마스크 수·평균 점수 (저장소 밖
  작업 디렉터리).
