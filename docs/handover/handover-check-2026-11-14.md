# 인수 준비 점검 2026-11-14

[인수인계 첫 화면](README.md) · [문제 레지스트리](issues.yaml)

질문은 하나였다. 개발자가 이 저장소를 받아 바로 고치고 유지할 수 있는 형태인가. 문서를 읽고 판단하는
대신 세 가지를 실제로 해 보았다.

1. CI와 전체 검사를 지금 상태에서 돌렸다.
2. 저장소를 처음 보는 개발자 역할의 독립 검토자 세 명에게 문서만으로 과제 하나씩을 풀게 했다
   (읽기 전용, 서로 결과를 모른다). 답과 "막힌 곳"을 코드와 대조했다.
3. 두 번째 실영상 실행(2026-11-09~10)의 수치를 레지스트리의 기존 문제와 맞춰 보았다.

## 결론

구조·규칙·시험은 넘겨받을 수 있는 상태다. 다만 점검 전에는 첫날 걸리는 문제가 넷 있었고 이번에 고쳤다.
남은 것은 문서가 아니라 제품의 미완성 부분이다 (실영상 품질, GPU 미사용, 실제 장비 미검증).

| 항목 | 점검 전 | 지금 |
| --- | --- | --- |
| CI | 2026-11-04 마지막 커밋부터 세 작업 모두 실패 | 원인 둘을 고침 (아래 1절) |
| 새 컴퓨터의 `make check` | 우분투 24.04 기본 파이썬(3.12.3)에서 시험 1개 실패 | 통과 (아래 2절) |

| GPU 추론 | 코드 세 곳이 CPU 고정, 문서에 없음 | 문제 등록(F-PAR-98), [구조 지도](architecture.md)에 표 |

## 1. CI가 열흘 동안 실패하고 있었다

2026-11-04의 GR00T·scene3d 커밋(787f27f)부터 CI 세 작업이 모두 실패했고, 그 뒤 아무도 보지 않았다.

- **FFmpeg 없음.** GR00T 내보내기 시험이 `ffmpeg`을 부르는데 CI 러너에 FFmpeg가 없었다. 다른 미디어 시험은
  FFmpeg가 없으면 건너뛰게 되어 있어, 그 시험들은 CI에서 한 번도 돈 적이 없었다. CI가 FFmpeg를 설치하고
  버전을 찍게 했고, GR00T 시험도 같은 건너뛰기 규칙을 따른다. 실행 파일이 없을 때 내보내기는 고칠 설정을
  알리는 오류를 낸다.
- **러너 이미지 변경.** 러너가 `ubuntu-26.04`로 바뀌면서 `sleep`이 Rust coreutils가 되었다. 이 `sleep`은
  다른 이름의 심볼릭 링크로 부르면 실행을 거부한다. 콘솔 시험 하나가 그 방식에 기대고 있었다. 그 이름의
  파이썬 스크립트를 돌리게 바꿨다.

교훈: 푸시 뒤 CI 결과를 확인하는 단계가 작업 순서에 없었다. [인수 기준](acceptance.md)의 검수자 체크리스트는
"CI `check`·`services` 성공 (실행 링크)"을 요구한다. 혼자 푸시할 때도 같은 확인을 한다.

## 2. 파이썬 패치 버전에 따라 명령줄 해석이 달랐다

파이썬 3.12.7·3.13.1 전의 argparse는 `dlp calib assign <기기> --reason R s001 s002`처럼 위치 인자 사이에
옵션이 끼면 뒤의 세션 ID를 받지 못한다. 3.12.6, 3.12.7, 3.13.0, 3.12.13으로 경계를 확인했다. CI는 최신
3.12를 받아 통과하고, 우분투 24.04의 시스템 파이썬 3.12.3에서는 시험이 실패했다. `dlp_cli.main.parse_cli_args`가
남은 값을 표시된 위치 인자에 넣어 버전과 관계없이 같게 읽는다. 문서에 적힌 순서(세션 ID를 기기 바로 뒤에)는
어느 버전에서나 되었다.

## 3. 처음 보는 개발자 세 명의 과제

| 과제 | 찾은 답 (코드와 대조) | 막힌 곳 |
| --- | --- | --- |
| 알려진 결함 F-PMS-05를 고치는 계획 | 원인 위치(`dlp_privacy/pipeline.py`의 `detect_video`, 같은 ms로 반올림되는 두 프레임)와 닫는 절차가 맞았다. 고치는 방식 둘(프레임을 건너뛸지, 탐지를 합칠지) 중 어느 쪽이 맞는지는 문서로 정할 수 없다고 보고했다 | 결함 ID에서 코드로 가는 길이 문서에 없어 검색했다. 구조 지도와 변경 표의 프라이버시 행에 `pipeline.py`·`tracker.py`가 없었다. 닫는 절차가 네 곳에 나뉘어 있었다 |
| 블러 대상(차량 번호판) 추가와 자동 탐지 | 사전 한 곳과 탐지 정책 두 곳을 함께 고쳐야 하고, 등록·재탐지·검수 프로젝트에 미치는 영향까지 맞았다 | 블러 대상을 더하는 절차 문서가 없었다. 정책 대상과 사전이 어긋나도 잡는 검사가 없었다. `extra_targets_v1` 안내는 코드가 읽지 않는 값이다 |
| GPU 서버로 자동 라벨·블러 탐지 돌리기 | CPU 고정 세 곳(`dlp_models/onnx.py`, `adapters/rtmpose.py`, `adapters/mediapipe_models.py`)과 의존성·버전 표기 문제를 찾았다 | GPU 안내가 어느 문서에도 없었다. ADR 0009의 "onnxruntime-gpu로 바꾸면 된다"는 코드와 맞지 않는다. `prelabel.yaml` 머리말의 해시 대상 절 목록이 낡았다 |

세 명 모두 답에는 닿았다. 걸린 시간의 대부분은 "어느 파일인가"를 찾는 데 들었다.

## 4. 고친 것

- [파일 지도](file-map.md): 코드·설정·스크립트 파일마다 역할 한 칸. 각 파일 맨 위 설명의 첫 문단에서
  `make file-map`이 만들고 `make contracts`가 일치를 검사한다. 역할을 적지 않은 새 파일은 검사에서 걸린다.
  역할 문장이 한두 단어뿐이던 모듈 21개와 온톨로지 사전 파일 8개의 첫 문단을 보강했다.
- [변경 안내](change-guide.md): "알려진 결함 하나를 고칠 때", "블러 대상을 하나 더할 때"의 순서. 변경 표의
  프라이버시·모델 행에 빠진 진입 파일.
- [구조 지도](architecture.md): 프라이버시 진입 파일(`pipeline.py`, `tracker.py`, `detectors/`, `render.py`와
  `rendering.py`의 구분), 모델별 추론 런타임과 CPU로 고정한 위치 표.
- `config/policies/prelabel.yaml` 머리말: 해시에 들어가는 절 목록(14개)을 코드와 맞췄다. 추론 간격 주석에
  "줄이면 버전이 바뀌어 모든 세션이 다시 돈다"를 적었다 (`privacy.yaml`도 같다).
- `tests/test_policy_consistency.py`: 탐지 정책의 블러 대상이 온톨로지 사전에 있는지 본다.
- 문제 ID 형식: 영역별 번호가 99를 넘어도 되게 했다 (`tests/test_issue_registry.py`, PAR이 98까지 찼다).

## 5. 고치지 않고 등록한 것

| ID | 내용 | 왜 지금 고치지 않았나 |
| --- | --- | --- |
| F-PAR-98 | 모델 추론이 CPU에 고정돼 GPU 서버를 써도 빨라지지 않는다 | GPU가 없어 결과를 확인할 수 없다. GPU판 onnxruntime은 CPU판과 한 환경에 둘 수 없어 선택 설치로 나눠야 하고, GPU와 CPU의 결과가 조금 다를 때 라벨 버전을 가를지는 소유자가 정할 일이다. OWLv2 가중치가 양자화본이라 GPU에서 얼마나 빨라지는지도 재 봐야 안다 |
| F-SCH-35 | `config/defaults.yaml`의 `privacy.extra_targets_v1`을 읽는 코드가 없다 | 지우면 설정 계약이 바뀐다. 확장 블러 대상을 정할 때 함께 정리한다 |

## 6. 두 번째 실영상 실행 (2026-11-09~10)

첫 파일럿과 같은 가사 영상의 다른 구간이다 (바로 세운 1080p 30 fps). CPU 4코어, GPU 없음. 영상과 프레임은
저장소에 넣지 않았다. 새 결함은 없었고, 기존 문제의 수치가 다른 구간에서도 같게 나왔다.

| 항목 | 값 | 관련 문제 |
| --- | --- | --- |
| 처리 시간 (90초 구간) | 블러 탐지 18분 + 자동 라벨(손·객체·도구·접촉) 16분 = 영상 길이의 약 23배 | F-PAR-98 |
| 블러 트랙 (90초) | 1669개. 26초 구간 336개(반사 206, 얼굴 91), 14초 구간 264개(얼굴 106, 반사 82). 화면에 다른 사람은 없다 | F-PMS-31 |
| 도구 박스 (90초) | 389개, 신뢰도 최고 0.59·중앙값 0.22. 설거지·택배 장면에 거울 34, 대걸레 32, 변기 솔 25 | F-PAR-60, F-SCH-26 |
| 사람 자세 (26초·14초) | 착용자 억제 뒤에도 coco17 트랙 19·9개(신뢰도 0.31~0.43)가 남았다. 긴 것부터 8개를 프레임에 겹쳐 보니 모두 착용자 자신의 팔·몸통·다리 위였다 | F-PAR-66 |
| 팔 골격 (26초·14초) | 팔꿈치가 보인다고 판정한 키프레임: 왼팔 50/106·70/99, 오른팔 101/141·62/105 (정답 없음) | F-PAR-66 |
| 모양 마스크 (26초) | 트랙 21개, 마스크 254개, 프레임당 1.34초. 박스와의 IoU p10/50/90: 객체 0.53/0.80/0.92, 손 0.66/0.76/0.83 | F-PAR-68 |

환경에서 확인한 것:

- Docker 이미지를 받을 수 없을 때(Docker Hub 요청 제한) 시스템 PostgreSQL과 로컬 저장소(`--store local:<폴더>`)로
  수집·동기화·블러 탐지·자동 라벨이 끝까지 돈다. 절차는 [환경 준비](development.md)에 적었다.
- CVAT v2.78 왕복: 제품 변환 함수로 작업 넷(라벨·블러 × 두 구간)을 만들고 그대로 다시 읽으면 833개가 모두
  "승인"으로 나왔다. 화면에서 트랙 하나를 지우고 저장하면 "삭제 1"로 잡혔다.

## 7. 넘겨받는 사람이 알아야 할 크기

- 패키지 21개, 소스 약 9만 7천 줄, 시험 약 6만 줄. `make check`는 시험 1,900여 개를 7~8분에 돈다.
- 레지스트리에 열린 문제가 120건 남짓 있고 그중 높음이 7건이다. 높음 7건은 문서나 구조의 문제가 아니다:
  인증·테넌트(S1), CVAT 원본 사본(S2), 의존성 취약점(S3), 라이선스 결론(S4), 실제 학습 경로(T1),
  실영상 블러 과탐지(F-PMS-31), 실영상 도구 과탐지(F-PAR-60).
- 실제 모델을 붙이지 못하고 stub만 둔 곳은 `make todo-models`가 보여 준다.
